# 协作约束：Claude 与 Codex 协同开发

本文件约束本项目中 **Claude** 与 **Codex** 两个 AI 的分工与交接规则。
两者都必须先遵守 `AGENTS.md` 与 `docs/DEVELOPMENT_LOOP.md`，本文件只补充「两人怎么配合」。

---

## 一、角色分工

| 角色 | 职责 | 不做的事 |
|---|---|---|
| **Claude（规划 + 修改/审查）** | 读代码、拆解需求、写任务清单、定验收标准、审查 Codex 的产出、做小幅修正与重构 | 不负责从零大规模写功能代码（除非 Codex 卡住或需求很小） |
| **Codex（执行）** | 按 Claude 给的任务清单写实现代码、写测试、跑验证、提交 | 不擅自扩大需求范围、不改架构、不做清单外的功能 |

一句话：**Claude 出图纸和验收，Codex 干活，Claude 验收并修补。**

---

## 二、标准工作流（一个 Loop）

```
Claude 规划  →  Codex 执行  →  Claude 审查/修改  →  验证全绿  →  提交推送  →  更新 progress.md
```

1. **Claude 规划**
   - 在 `docs/` 下产出/更新任务清单（如 `docs/METRICS_TODO.md`），包含：要做什么、改哪些文件、验收标准、优先级、边界情况。
   - 单个 Loop 只交付一个可验证的纵向切片（遵守 `DEVELOPMENT_LOOP.md`）。

2. **Codex 执行**
   - 严格按清单实现，**测试先行**：先写失败测试，再写最小通过代码。
   - 只改清单点名的文件，不顺手重构无关代码。
   - 遇到清单没覆盖的歧义，**停下来标注问题**，交回 Claude，不自行拍板。

3. **Claude 审查/修改**
   - 检查：是否符合验收标准、是否有 lookahead（必须 next-bar 执行）、边界处理、测试是否真覆盖。
   - 小问题 Claude 直接改；方向性问题打回 Codex 重做。

4. **验证全绿**（每个 Loop 结束都必须跑，任一失败先修再继续）
   ```
   python -m pytest
   python -m ruff check .
   python -m aetf_momentum.app.cli --help
   ```

5. **提交 / 更新进度**
   - 开发分支：`claude/repo-overview-roadmap-i5ts8m`（未经许可不推 `main`）。
   - 每个 Loop 结束更新 `progress.md`：已完成 / 未完成 / 已知风险 / 下一步建议。

---

## 三、交接契约（避免互相踩脚）

- **唯一事实来源**：当前任务状态以 `docs/` 下的任务清单 + `progress.md` 为准，不靠口头记忆。
- **任务清单格式**：用 `- [ ]` / `- [x]` 勾选框表示进度，谁完成谁打勾并署名（`(codex)` / `(claude)`）。
- **谁在改**：同一时间一个文件只由一方修改。Claude 审查期间 Codex 不动同一文件，反之亦然。
- **提交信息**：写清是规划、实现还是修复，便于回溯哪一步是谁做的。
- **不重复造轮子**：Codex 实现前先确认 Claude 清单里指定的复用点；Claude 审查时优先建议复用而非新增。

---

## 四、红线（双方都不可违反）

- 不实现实盘交易，第一阶段只做研究与回测。
- 所有信号必须 next-bar 执行，绝不在产生信号的当根收盘价上成交。
- 业务逻辑全部放在 `src/aetf_momentum/` 下，不把 notebook / 一次性脚本当系统核心。
- 不复制第三方框架源码，只借鉴架构思路。
- 验证不绿不收工。
